Project Name: Community Issue Tracker

Framework: Frappe Framework / Web Development

Author: Chinthal Sandeep

Focus Area:
Technology for Social Good & Civic Tech

Project Overview

Civic engagement relies on seamless communication between citizens and the organizations that serve them. To facilitate this, I developed the Community Issue Tracker, a dynamic web application designed to empower community members to report local infrastructural and civic issues—such as broken streetlights, potholes, or waste management problems. Built using the Frappe Framework, this platform bridges the gap between citizens reporting problems and administrative staff resolving them.

System Architecture & DocTypes

To ensure the database was highly relational and scalable, I engineered the backend using two primary Data Models (DocTypes):

  • The "Issue" DocType: This is the core engine of the application. It captures everything needed for a rapid response, including an auto-generated Issue ID (e.g., ISSUE-00001), Title, and a rich Text Editor for descriptions. Crucially, it integrates Geolocation mapping so staff know exactly where the problem is. It also links highly relational fields like Reported By, Assigned To, and Status (Submitted, In Progress, Resolved).
  • The "Issue Category" DocType: A secondary master-data model used to standardize ticketing. It allows administrators to define and describe categories like "Infrastructure", "Sanitation", or "Safety", keeping the database organized and query-friendly.

Role-Based Access Control (RBAC)

Data security and workflow integrity are critical for public-facing portals. I implemented strict role-based permissions to ensure users only see what they need to:

  • Community Resident: Granted Create and Read permissions restricted to their own data. They can submit new tickets and track the real-time status of their specific reports.
  • Organization Staff: Granted full administrative privileges (Read, Write, Create, Delete). This allows backend personnel to update statuses, assign workloads to specific team members, and moderate the portal.

Dashboard & Analytics

For the Organization Staff, efficiency is key. I designed an interactive Issues Dashboard that provides a bird's-eye view of civic health. It features live metric cards for Total New Issues and a visual breakdown chart comparing issues by their current status. Below the charts, a dynamic list highlights Unassigned Issues, ensuring no citizen's report slips through the cracks.

Additionally, I built an All Issues Report—a highly filterable matrix containing columns like Issue ID, Category, Date Reported, and Assignment data, allowing staff to export and analyze long-term civic trends.

The Resolution Workflow in Action

  • 1. Submission: A Community Resident logs securely into the portal, drops a Geolocation pin on the map, uploads the issue details, and submits. The system defaults the ticket to "Submitted".
  • 2. Triage & Assignment: Organization Staff monitor the live dashboard, spot the new ticket in the "Unassigned" queue, allocate it to a specific field worker, and shift the status to "In Progress".
  • 3. Resolution & Documentation: Once the physical work (like fixing the pothole) is completed, the staff member updates the ticket with detailed Resolution Details and officially marks it as "Resolved".
  • 4. Transparency: The dashboard analytics and reports update autonomously in real-time, and the citizen can log in to see that their community has been improved.

Advanced Feature: Workflow State Machine

For the exploration component of this project, I chose to implement complex Workflows. While the standard Frappe framework allows users to save and edit documents using simple permissions, it does not inherently enforce a strict business process. To prevent unauthorized status changes (e.g., jumping straight from "Submitted" to "Resolved"), I engineered a strict Workflow state machine to govern the lifecycle of every "Issue" document.

  • Process Control: Designed a linear path (Submitted → In Progress → Resolved) that strictly prevents users from skipping steps.
  • Role-Based Transitions: Utilized Transition Rules so that moving a ticket from "Submitted" to "In Progress" (via the "Start Work" action) is strictly restricted to the Organization Staff role.
  • Data Integrity & Locking: Configured the "Resolved" state with DocStatus: 1 (Submitted). Once an issue is marked as resolved, it becomes strictly read-only, preventing any tampering with the historical record.

Development Challenges & Troubleshooting

Implementing Workflows introduced several backend complexities. Here is how I debugged and resolved them:

A. Configuration Logic

Challenge: Aligning "States" with actionable "Transitions" without creating dead ends.

Solution: Meticulously mapped the Next State rules and manually linked the Workflow State Field to my existing status field, ensuring the visual frontend dropdown updated perfectly with the backend logic.

B. Validation Errors

Challenge: Encountered a mandatory field error ("Only Allow Edit For") when trying to lock the "Resolved" state.

Solution: Discovered that Frappe requires a role assignment even for read-only states to satisfy validation. Assigned the Organization Staff role to clear the error and successfully lock the document.

C. Permission Testing

Challenge: Action buttons (like "Start Work") failed to appear on the interface despite having an Administrator account.

Solution: Realized the Workflow engine checks for exact roles, not just admin privileges. Navigated to the User List, manually assigned the Organization Staff role to my account, and successfully executed the workflow.

Implementation Status

The feature has been successfully deployed. The application now features dynamic "Action" buttons that replace the standard save functionality. This implementation significantly enhances the reliability of the Community Issue Tracker, transforming it from a simple data entry form into a highly managed, professional workflow system.
